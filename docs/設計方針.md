# ToDoリスト 設計方針

このアプリの「何のために・誰のために・何を守って作るか」をまとめたもの。
機能を追加・修正するときは、まずこの文書に照らして判断する。
使い方や起動方法は [README.md](../README.md)、起動・反映・トラブル対処は [引き継ぎガイド.md](引き継ぎガイド.md) を参照。

最終更新: 2026-11-11(新規タスクの開始日初期値を追加)

---

## 1. 目的と背景

- 現在チームでは **Excel の日報** を提出しているが、うまく機能していない。
- その代替として、各メンバーが **個人の ToDo として日々使う** ツールを作り、
  その記録を **上司が閲覧** できるようにする。
- 上司が知りたいことは次の 2 点だけ。
  1. **異常に時間をかけている作業** があれば察知し、注意したり原因を知りたい。
  2. **困りごとを抱えているメンバー** がいれば察知してサポートしたい。
- **工数を集計して見積もりに使う、といったデータ収集は目的ではない。**
  時間の記録はあくまで「異常の察知」のためにある。

## 2. ロードマップ(段階)

| 段階 | 内容 | 状態 |
|---|---|---|
| ① 個人試作 | 開発者が 1 人で使い、使いやすくなるまで磨く | **完了**(2026-10-28 引き継ぎ。次の段階の作業は [次の作業.md](次の作業.md)) |
| ② チーム共有 | Azure App Service にホストし、チーム全員がブラウザで使う。ログインで本人を識別 | 未着手 |
| ③ 上司画面 | 上司役がメンバー全員の状況(異常・困りごと)を一覧できる画面 | 未着手 |
| ④ デプロイ | App Service へ **手動** デプロイ。Git 連携は環境が整ってから移行 | 未着手 |
| ⑤ Copilot 連携の作り直し | MCP サーバーがホスト先の API を本人の権限で叩く形にする | **一時停止中**(2026-10-27。画面から外し、コードは残置) |

作業の優先順は ① → ② → ③ → ④ → ⑤。引き継ぎ後は、① の続き(実際に使って細かく直す)→ 上司への報告 → ②・③ → ④ の順に進める(2026-10-28 の引き継ぎ時の取り決め。[次の作業.md](次の作業.md))。

## 3. 利用者と権限

- チームは **1 つ**。
- **上司役は複数**(現在 3 人: 上司 1 人+役職者 2 人)。
  上司役は **設定(環境変数)にメールアドレスを列挙** して決める。Entra ID のグループ連携はしない。
- **メンバーは自分のタスクだけ** 見える・操作できる。
- **上司役はメンバー全員のタスクを閲覧** できる。メモや振り返りの本文も閲覧してよい
  (ただし上司は全文を読む時間がないので、画面では要点が先に見える形にする)。
- 他人のタスクの **編集は本人のみ**。

## 4. 上司画面で拾う「異常」

上司画面では、次の条件に当てはまるタスクを人ごとに一覧する。

| 種類 | 条件 | 表示するもの |
|---|---|---|
| 長時間化 | 同一タスクの **累計作業時間が 5 時間以上**(既存の `LONG_RUNNING_MINUTES`) | タスク名・担当者・累計時間 |
| 期限超過 | 期限日を過ぎて未完了 | タスク名・担当者・期限 |
| 困りごと | 🚩 フラグが立っている | タスク名・担当者・**フラグの理由(note)** |

- 「3 日以上進行中のまま」は **拾わない**(ヒアリングで不要と判断)。
- 「🚩 が立ってからの経過日数」「1 人あたりの 🚩 件数」なども **今は不要**。
  フラグが立っているタスクと理由がわかれば十分。

## 5. やらないこと・後回しにすること

- **AI による要約は今はしない。** Azure OpenAI などの従量課金を避けるため。
  将来やるなら、上司が自分の Copilot Chat から MCP ツール(例: `get_team_summary`)を呼び、
  要約は Copilot 側にやらせる形にする(Azure 側の費用ゼロ、上司の Copilot クレジットのみ消費)。
  そのため、集計ロジックは画面と MCP の両方から呼べる関数として切り出しておく。
- 工数集計・レポート出力・見積もり支援。
- Entra ID グループによる権限管理。
- タスクの削除を Copilot(MCP)から行う機能(誤操作防止のため引き続き提供しない)。

## 6. 画面と機能の方針(2026-10-27 決定)

### 6.1 画面構成

「タスク」「日報」「アーカイブ」の 3 画面。以前の「今日」「タスク一覧」「今日の振り返り」は二重管理で見にくいため廃止した。

### 6.2 タスク画面: 焦らず目の前に集中できること

- 1 画面を **「今日やる」と「明日以降にやる」の 2 段** に分ける。
  名前の経緯: 「今日やる/あとでやる」→「今日/明日以降」→ 期限の「今日」と紛らわしいため「今日やる/明日以降にやる」(2026-10-28)。段の名前には「やる」を付け、期限の話ではなく取り組む日の話だとわかるようにする。
  2 段に分けるのは、たくさんのタスクが見えて焦り、パフォーマンスが下がるのを防ぐため。
  - 今日やる: 自分で選んだもの + 期限が今日以前 + 進行中 + 今日完了したもの。
  - 明日以降にやる: 最初は閉じる。開いたときは少し淡くするが、読める濃さは保つ。期限が近い順。
  - **並べ替え**(2026-11-10): 初期は両段とも期限の近い順。列見出しから進捗・タスク名・期限・重要度・緊急性を昇順/降順に切り替える。選択と向きはブラウザに記憶し、通常画面とミニ表示で共有する。今日完了した一覧は完了時刻順のまま。
    親の順は親自身の値で決め、子は親の直下を保って選択した値で並べる。進捗は単独タスクなら未着手→進行中→完了、親なら子の完了割合で比較する。待ちタスクは各段の後ろ。期限なしの既存タスクは期限順の最後に置く。タスク名はブラウザ標準の日本語文字順を使い、漢字の読み仮名は推測しない。
  - **新規追加時の期限**(2026-11-10): 期限欄を空欄にしてタスクを追加した場合は当日を設定する。ただし親を指定して子を追加するときは期限なしのままとし、親子の段を暗黙に変えない。既存の期限なしタスクは一括変更せず、期限なしのまま編集保存できる。
  - **開始日**(2026-11-10): 将来の「週スケ画面」で、報告日以前に開始予定のタスク数(予定着手数)を数えるため、タスクに任意の開始日を保存する。開始日は期限の後にできない。新規の親なしタスクは開始日が空欄なら当日を設定し、期限が当日より前なら期限日を設定する。親の下に追加する子タスクは空欄のままにする。繰り返しの次回分では期限と同じ日数だけ開始日をずらし、開始日が未設定なら未設定のままにする。今回は入力と保存だけで、一覧の列・週スケ画面・集計にはまだ使わない。
  - 段を移すボタンは **移動先の段の名前と向き**(「明日以降に ↓」「↑ 今日やる」)にする。「今日から外す」はわかりにくかったため。
  - 移したあとは「元に戻す」付きのお知らせを出す(閉じた段へ移った行を見失わないように)。
  - ボタンはすべての未完了タスクに出す。期限切れ・進行中で自動的に入ったものを「明日以降にやる」にした場合は、その日だけ下の段に置き、翌日はまた今日やるに戻す。
  - 日報へ移るのは上のタブだけにする。タブと同じ働きのボタンは置かない。
  - 今日やるに入れて終わらなかったものは翌日も今日やるに残る(1 日 1 回だけ持ち越す)。
- 今日やるかどうか以外の整理の軸(今日/今週/いつか、案件ごと等)も検討したが、毎朝の仕分けが手間になるので採用しない。
- **タスク行は表の形**(2026-10-28 決定)。各段の先頭に列見出し「日報・進捗・完了・タスク・期限・重要度・緊急性・状態・取り組む日」を置き、すべての行で列の位置をそろえる。「進捗・完了」「重要度・緊急性」はそれぞれ1列。期限の列は常に出す。「移動」は用途がわかる「取り組む日」に改称し、移動先を示すボタンは残す(2026-10-29)。
  - 2026-10-29から％の表示・操作を廃止。子のないタスクは「未着手／進行中／完了」とし、「作業を始める」「済」で操作する。開始ボタンは紺の塗りボタンにして目立たせる。未着手・未完了に戻す操作も付ける。
  - 子のある親は「2/5件完了」＋操作できない細いバーで表示。子1件は同じ重さで数える。タスク・ミニ表示・日報・アーカイブで同じ表示を使う。
  - 日報に入れる操作は「日報」と書いた小さな判子(回覧印)。完了のチェックと形を変えて混同を防ぐ。
- **相談したい(困りごと)**: 押すと付箋が付き、その場で理由を一言書ける(候補から選ぶだけでも可、任意)。
  「困った」は弱音に聞こえて押しにくいため、「相談したい」「解決した」という言葉にした。上司の画面では「困りごと」として扱う。
  付箋には「書いた内容は上司の画面に表示されます」と明示し、隠さない。
- **返事待ち** の状態を持つ。他人の返事待ちなど自分では進められないもの。何を待っているかを一言書ける(本人用のメモ)。
  困りごととは別で、上司への目印にはしない。各段の後ろに並べる。解除は「再開する」。
- 状態ボタン(相談したい・返事待ち)は普段は控えめな文字で出し、行にマウスを乗せたときと状態が付いているときだけはっきり見せる(1 行の操作の多さを抑えるため)。
- この再設計は、タスク管理アプリが使われなくなる原因の調査(入力の手間、未完了を責める表示、職場で見られることへのためらい等)と、複数の AI による案・批評を突き合わせて決めた。
- **親の着手状態は子から計算し、完了だけ利用者が選ぶ**(2026-10-29決定、2026-10-30操作を変更)。全件未着手なら未着手、一部着手・完了なら進行中。最後の子が完了しても親は自動完了せず、進捗欄の「親も完了にする」ボタンを押した場合だけ完了する。ブラウザーの確認ポップアップは出さない。タスク・ミニ表示で同じ動作にする。
  結び付け・解除・削除によって残った子が新しく全件完了になった場合も同じボタンを出す。再読み込みしても、親が未完了で子が全件完了ならボタンを使える。子が0件なら完了ボタンを出さず、その時点の状態の単独タスクにする。起動時は既に完了した親の状態と完了日を保つ。
  未完了の子が残る親の完了は認めず、親から子をまとめて変更しない(誤操作で多くの子を巻き込まないため)。親だけ未完了に戻すことは認める。アーカイブの子を未完了に戻せば、親も再計算し、親子でタスク画面へ戻る。
- サブタスクは親の直下に並べる。**親子は必ず同じ段**に置く(子が1つでも今日やるなら親も今日やるに出す)。段の移動は親の行で親子まとめて行い、子の行には移動ボタンを出さない。親より先に終わった子タスクは、親が完了した当日まで親の下に完了日付きで残し、翌日から親子でアーカイブへ移す。
- **子タスクの収納**(2026-10-29): 通常画面・ミニ表示で、親ごとに「全部表示／完了だけしまう／全部しまう」を選べる。初期値は「完了だけしまう」。子の総数・完了数・実際に収納している件数は親に表示し、隠れた未完了の子に相談中・期限超過があれば、その件数も出す。
  表示だけを切り替え、段の件数・進捗・日報への選択・記録は変更しない。通常・ミニ別、親別にブラウザへ記憶し、操作後や再読み込みでも選択を保つ。保存できない場合も現在の画面内では保ち、次回に記憶できないことを案内する。
  開閉は行の移動と同じView Transitionsを使い、OSの動きを減らす設定では止める。新しく完了した子は完了演出を見せてからしまう。保存を拒否された子の編集欄は隠さない。日報・アーカイブには収納機能を付けない。
- 既存の％は、0→未着手、25〜75→進行中、100→完了として引き継ぎ、子のある親だけ再計算する。古い列は削除せず、作業時間などの記録も保つ。起動時の整理で繰り返しの次回分を作らない。
- **既存タスクの結び付け・解除**(2026-10-29): 子にしたいタスクの編集欄で親を選び、保存して反映する。候補は本人の未完了の親だけで、絞り込み中も全案件から選べる。自分自身・他人のタスク・完了した親・子を持つタスクの子化は認めず、親→子の1段に限る。
  同じ欄から親を外して独立させられる。別の親に直接移さず、いったん外す。作業時間・日報・メモ・タグなどの記録と本人の状態は保ち、残った親は再計算する。段が変わった場合は移動先を画面で知らせる。
- **繰り返しは親側だけで管理**(2026-10-29): 利用者が親の「親も完了にする」ボタンを押したときだけ、次回の親子セットを全件未着手で作る。ボタンを押すまでは作らない。タイトル・メモ・重要度・緊急性・タグを引き継ぐ。子の期限は元の親との日数差を保ってずらす(親に期限がなければ完了日が基準)。期限のない子はそのまま。作業時間・日報への選択・相談・返事待ちは引き継がない。
  子の個別設定が残る場合、利用者の確認なしに外さない。親の編集欄で対象件数と確認欄を出し、確認後に外す。未確認なら理由を表示して操作を断り、途中で保存した内容も元に戻す。完了の取り消し・やり直しで同じ次回分を二重作成しない。

- タスク追加は Enter だけで追加できる手軽さを保ち、必要なときだけ入力欄の下の「詳しく書く」を開いて、追加先・重要度・緊急性・期限・メモを入れられるようにする。
  入力欄はタスクの操作で描き直されない場所に置き、開いた状態や書きかけの内容が消えないようにする。

### 6.2.1 アプリとして使う・ミニ表示(2026-10-28 決定)

- デスクトップアプリ化は **ブラウザの「アプリとしてインストール」(PWA)** で行う。PC にプログラムを入れず、サーバー側(今はローカル、将来は Azure)を更新すれば全員が最新になる。
  Electron などの本物のデスクトップアプリや Windows のウィジェット欄は、配布・更新・保守の負担が大きいので採用しない。
- 小さく使うために **ミニ表示(`/mini`)** を持つ。今日やるタスクだけを並べ、共通の件数・状態表示と「作業を始める」「済」などの状態操作を使える。細かい操作はタスク画面で行う。
- ミニ表示は普通の小さな窓で開き、準備ができたことを確認してから元画面を閉じる(2026-10-29変更)。ブラウザに閉鎖を拒否された場合は元画面の自動更新と操作を止め、手動で閉じる案内を出す。ブラウザ側の制限を回避する細工はしない。
  「全体表示に戻る」では元画面が残っていれば再利用し、なければ全体画面を新しく開く。準備確認後にミニ表示を閉じる。同じ表示の窓は名前付きで再利用する。書きかけは切替前に確認し、保存・通信中は切り替えない。開けない・閉じられた・準備を確認できない場合は元画面を残して案内する。
  準備の確認には、同じ接続先からのメッセージと窓・確認番号・表示種類の照合を使う。固定時間を待つだけで元画面を閉じない。休止した画面から再開する場合も、相手側の書きかけを確認してから切り替える。
- 「小窓で浮かせる」(Document Picture-in-Picture)も試作したが、ミニ表示で十分なため外した(2026-10-28)。
  常に手前に出したい人は PowerToys の「常に手前に表示」(Win + Ctrl + T)を使う。
- **インストールのボタンは Azure に載せるまで出さない**(`main.py` の `SHOW_INSTALL_BUTTON = False`)。アプリはアドレスごとに別扱いのため、ローカル(127.0.0.1)で入れると Azure 移行時に入れ直しになるから。設定ファイル・アイコン・service worker は残してあり、Azure に載せたら `True` にするだけで使える。
- service worker は画面やデータを保存しない(常にサーバーの最新を表示する)。サーバーにつながらないときに案内を出すだけ。

### 6.3 日報: Excel 日報の代わり

- タスク画面で日報に書くタスクを選び、日報画面で時間などを入れて提出する。Excel 日報の出力はしない。
- **入力途中で消えないこと**。選択も入力もその都度サーバーに下書き保存する(ブラウザバック対策)。
- 1 人 1 日 1 件。提出後も修正でき、修正すると「修正あり(未提出)」になる。
- 作業時間は **時:分** で入力する(分で計算させない)。
- **基本勤務時間は 7:45(休憩を除く実働)**。作業時間の合計と、その差(残業時間)を自動で出す。
- 「作業時間」と「勤務形態・休暇など」は独立したボタンで入力をON/OFFする。初めて開く日は両方ONで、状態は日報ごとに保存する。OFFでも入力済みの値・作業時間記録・選択したタスクは消さず、ONで再表示する。作業時間がOFFのときは基本勤務時間・作業時間の合計・差を表示しない。保存済みの値は保持し、ONに戻すと合計を再表示する。OFFの項目は入力・選択なしで提出できる。切り替え直前の入力も保存し、読めない時刻があれば入力欄とON/OFFを保って案内する。
- 勤務形態は「テレワーク」1個のチェックボックスにする(チェックあり＝テレワーク、なし＝出社)。休暇など(早退・時間休・午前休・午後休)はボタンで付ける。**時間休・午前休・午後休は同じ日に 2 つ付かないので排他**(どれか 1 つ)。早退はそれらと同時に付けられる。備考・所感はON/OFFに関係なく入力できる。
- 日報の作業時間はタスクの作業時間記録にも反映し、長時間化(累計 5 時間以上)の判定に使う。
- 今は「提出済み」として保存するだけ。上司が見る画面は段階③で作る。

## 7. 技術方針

### 7.1 構成

**チームで使う形の決定(2026-10-28)**: アプリとデータベース(SQLite のファイル)を App Service に丸ごと置く。Azure SQL は使わない。
- 比べた案: SharePoint のリストをデータベースにする案(Entra ID へのアプリ登録と管理者承認が要り、作り直しが大きい)、
  各自の PC で動かして上司に見せる分だけ SharePoint の共有フォルダへ書き出す案(Azure 不要だが、全員の PC で Python を動かし続ける保守が重い)。
  データベースのファイル自体を共有フォルダに置く案は、同時に書くとファイルが壊れるので不可。
- 決め手は保守性: 更新がサーバー 1 か所で済み、各 PC にはブラウザしか要らない。
- 負荷の実測(このPC、1回あたりのCPU時間): 自動更新の確認 4ms、タスク画面の表示 19ms、ボタン操作 21ms、日報の自動保存 15ms。
  10 人が 8 時間画面を開きっぱなしでも 1 日約 7.5 分、うち 6.7 分は 3 秒ごとの自動更新の確認。無料プランの上限(1 日 60 分)に収まる。
- **App Service に載せるときは、3 秒ごとの自動更新の確認(`/api/data-version`)を外すか間隔を延ばす。** 一時停止中の Copilot 連携のための仕組みで、チームで使う段階では不要。
- 無料プランは他のサービスと上限を取り合わないよう、このアプリ用のリソースグループ・プランを分けて置く。
- **無料プラン(Free / F1)の範囲**(2026-10-28 に Microsoft の公式ドキュメントで確認):
  - アプリごと: CPU 時間 1 日 60 分・5 分ごと 3 分、送信の通信量 1 日 165MB。超えるとその日(または 5 分間)は 403 で止まる。CPU と通信量は UTC 0 時(日本時間 9 時)に戻る。
  - プランごと: 保存領域 1GB、メモリ 1GB。1 つのプランにアプリ 10 個まで、無料プランは 1 リージョンに 10 個まで。
  - 独自ドメイン不可(`*.azurewebsites.net` の HTTPS は使える)、常時起動(Always On)なし、公式には開発・テスト向けの扱い。
  - CPU 時間は公式の説明では「アプリごと」だが、同じプランに複数のアプリを入れたときの扱いは文書からは断定できない。**このアプリ専用の無料プランを作って載せる。**
- **通信量の実測**(10 人・1 日・多めの見積もり): 圧縮なしで約 160MB(上限ほぼいっぱい)、圧縮ありで約 43MB、圧縮ありで自動更新の確認をやめると約 12MB。
  このため **応答の圧縮(GZip)を入れた**(2026-10-28)。CPU 時間より通信量のほうが先に上限に近づくので、画面を大きくするときは注意する。


- **FastAPI + Jinja2 + htmx + SQLite**。ビルド工程なし、依存は最小限。
- ホスト先は **Azure App Service(Linux, F1 無料プラン)**。
  - **費用は完全に 0 円** を目指す。常時起動は不要、アクセス頻度も低い前提。
  - DB は当面 **SQLite ファイル**をそのまま使う(App Service の永続領域 `/home` 配下に置く)。
    同時アクセスに弱いが、利用頻度が低いので「まずやってみる」。問題が出たら Azure SQL 無料オファーへ移行を検討。
- 認証は **Entra ID(Microsoft 365)** を使い、App Service の組み込み認証(Easy Auth)に任せる。
  アプリ側でパスワードを持たない。ログイン済みユーザーのメールアドレスをヘッダから受け取り、`users` テーブルと紐付ける。
- ローカル開発時は認証をバイパスし、固定ユーザーで動かせるようにする(今の動きを維持)。

### 7.4 見た目のルール

Excel 日報の代わりという出自に合わせ、**事務用品**をモチーフにしている(2026-10-27 決定)。
色は「上司が拾いたい目印」に集中させ、それ以外は紺と灰で静かに保つ。

| 意味 | 見た目 | 色(`app/static/style.css` の変数) |
|---|---|---|
| 背景 | 方眼ノート | `--paper` / `--grid` |
| 操作・選択中 | 紺 | `--navy` |
| 未着手 | 灰色の「未着手」札 | `--wait-bg` / `--ink-2` |
| 進行中 | 紺色の「進行中」札と丸い目印、淡い紺色の行 | `--navy` / `--on-accent` / `--navy-soft` |
| 完了 | 朱色の「済」判子(タスク行のタイトル横) | `--shu` |
| 期限超過 | 朱色の文字で「超過」 | `--shu` |
| 困りごと(相談中) | 黄色の付箋(行の左端に「困」、タスク名の下に理由の付箋) | `--fusen` |
| 日報に入れたもの | 紺の小さな判子「日報」 | `--navy` |
| 返事待ち | 灰色の札 | (灰) |
| 長時間(累計5時間以上) | 蛍光ペンのマーカー | `--marker` |

- 朱色は「判子」と「期限超過」以外に使わない。新しい目立たせ方を足したいときは、まずこの表に追加してから実装する。
- **未着手と進行中を文字と色で区別する**(2026-10-29)。子のある親・子・単独タスクで共通の状態札を使う。進行中の背景は親を濃い紺、子を淡い紺に分ける(2026-10-30)。相談中の行は黄色を優先し、状態札は残す。ミニ表示も同じ。何も操作していないときに点滅させない。
- **PC のブラウザ専用**。スマホ・タブレットには対応しない(使わないため)。狭い画面向けの CSS は書かない。
- タスクはカードを並べず、1 枚の帳票に罫線で行を並べる。
- **画面が遷移したり変化したりするときは、アニメーションで変化を見せる**(2026-10-27 決定)。欄の開閉、段の移動(行が新しい位置へ滑る)、タブの切り替え、ボタンの状態変化、日報の集計の数字の変化、行の削除など。
  ただし動くのは操作や変化への反応だけにし、何もしていないのに動く飾りは足さない。目玉はタスク行に「済」を押す一瞬。OS の「視差効果を減らす」設定が有効なら動きを止める。
- **完了演出は好みでON／OFFできる**(2026-10-29)。新しく完了を保存できた行だけに、大きな「済」の着地・弾みと二重の波紋を約1秒で出す。音・紙吹雪・励まし文は付けない。既定はONで、画面上部から変更できる。ブラウザ内に記憶し、開いている通常画面とミニ表示でも同期する。保存に失敗したら、現在の画面への反映は保ち、記憶できなかったことを明示する。
  OFFでは完了の判子を残して演出だけ止め、開閉や行の移動は変えない。ONへ切り替えただけでは過去の完了を再生しない。OSの動きを減らす設定を優先する。親の完了条件と進捗計算は変えない。
- **完了率や「さあ、始めましょう」のような励ましは出さない。** 今日のタスクが今日終わるとは限らないため、今日完了した件数だけを事実として表示する。
- **重要度・緊急性は編集欄の 低/中/高 ボタンで選ぶ**(3 段階しかないのでプルダウンにしない)。
- **ダークモードを持つ**(2026-10-28)。既定はパソコンの設定に合わせ、ヘッダーで「ライト」「ダーク」に固定できる。色はすべて `style.css` の `:root` の変数で指定し、ダーク用の値を別に持つ。モチーフ(付箋の黄色・朱の判子・蛍光ペン)はダークでも保つ。
  付箋の黄色の上の文字は両方とも濃い色(`--fusen-ink`)、暗い地に置く付箋系の文字は `--fusen-text` を使う。
- 本文の幅は 1200px(PC 専用)。薄い灰色の文字も、白地でコントラスト 4.5:1 以上を保つ。重要度・緊急性は「重要：高」「緊急：中」などの文字札にする(2026-10-29)。高は濃い紺、中は淡い青、低は薄い灰色で強弱を示し、ダーク表示では既存のテーマ色に合わせる。赤・黄・緑の信号色は使わず、完了・相談の目印と混同させない。行でのクリック変更は付けず、変更は編集欄の低/中/高ボタンで行う。
- 絵文字はアイコン代わりに使わない(環境で見た目が変わるため)。文字で書く。
- CSS の URL にはプログラムの内容から計算したバージョンが自動で付く(`app/version.py`)。手で番号を増やす必要はない。
