ToDoリスト / チーム利用への準備

Azure導入の進め方

ローカルで試作したアプリを、会社のMicrosoft 365ログインでチームが安全に使える状態へ。準備から本番利用まで、上から順に確認できるロードマップです。

最初にすること いまの状態 導入フロー 完了の目印

まず最初にすること

Azure管理者・Microsoft 365管理者に、利用できる環境と権限を確認する。まだ実データをAzureへ移したり、公開設定を変えたりする段階ではありません。

  • このアプリ専用のAzure環境を作れるサブスクリプションと担当者はいる？
  • Linux版App ServiceとPython 3.11を使ってよい？費用・無料枠・利用上限はどう確認する？
  • Entra IDの組み込み認証(Easy Auth)を有効にする権限はある？
  • 試験利用できるメンバー、上司役、利用開始時期は誰が決める？
  • タスクや相談メモをAzureに保存すること、保存先・バックアップ方法は社内ルールに合う？

いまの状態

認証とユーザー別データ分離の土台はできています。Azureの設定や、チームでの運用確認はこれからです。

土台あり

本人ごとのデータ分離

local / dev / entra の認証モードと、ユーザーごとのタスク・日報の分離を実装・テスト済み。Azureでの実認証は未確認です。

これから

Azure向けの設定と公開

Easy Auth、許可メール、Azureのホスト名、起動方法、永続DBの保存先は、Azure上で設定・検証する必要があります。

これから

上司画面と運用準備

上司が長時間・期限超過・相談中を確認する画面、バックアップと復元の手順は未実装・未確認です。

導入フロー

各段階の確認が済んだら次へ進みます。失敗や不明点があれば、実データを移さず、その段階で止めて原因を直します。

  1. 社内の利用条件を確認する

    最初の相談
    • Azureサブスクリプション、作成権限、担当管理者、利用リージョンを確認する。
    • 費用・プラン・上限・社内のデータ保存ルールを、作成前に最新情報で確認する。
    • 利用するメンバーと上司役のメールアドレス、試験開始の範囲を決める。

    次へ進む目印:環境を作る担当者と、許可された使い方が決まっている。

  2. アプリをAzureで動かせる形に整える

    コードと設定
    • ローカル専用のホスト名チェックを、許可したAzureのURLも使える設定にする。
    • 3秒ごとのデータ更新確認は、Azureでは停止または間隔を延ばす。
    • App Serviceの起動方法・ポートと、SQLiteを置く永続領域を実環境で確かめる。
    • Azureでは TODO_AUTH_MODE=entra を使い、開発用のユーザー切替は使わない。

    次へ進む目印:設定値がコードに埋め込まれず、ローカル動作と既存テストを保てている。

  3. 上司画面を作り、権限を確認する

    チーム機能
    • 上司だけが、長時間・期限超過・相談中と理由を閲覧できる画面を作る。
    • 上司画面も閲覧専用にし、タスクの編集は本人だけにする。
    • 上司以外が画面URLや操作先へ直接アクセスしても拒否されることを確認する。

    次へ進む目印:本人・上司それぞれの見える範囲がテストで確認できている。

  4. 本番データを入れない検証環境を作る

    Azure準備
    • アプリ専用のリソースグループとLinux App Serviceプラン・App Serviceを用意する。
    • Pythonの版、プラン、起動コマンド、HTTPS、永続ストレージを設定する。
    • まずは空のDBまたはテスト用DBで確認する。料金・無料枠・バックアップ可否は現在のAzure情報で再確認する。

    次へ進む目印:再起動後もテストデータが残り、費用と利用上限が把握できている。

  5. Entra IDログインと許可リストを設定する

    入口の保護
    • App ServiceのEasy AuthでMicrosoft Entra IDを有効にし、未ログイン利用を拒否する。
    • TODO_ALLOWED_USER_EMAILS、TODO_MANAGER_EMAILS、TODO_DATA_OWNER_EMAILを設定する。上司と既存データの持ち主も許可リストに含める。
    • Easy Authが渡すメール情報を実際のリクエストで確かめ、許可外メールと未ログインを拒否する。

    次へ進む目印:許可した人だけが入れ、ユーザー名が正しいデータ所有者に結び付く。

  6. アプリを手動で配置して、空データで動かす

    初回公開
    • 最初はGitHubからの自動公開を設定せず、手動で配置する。
    • タスク、WBS、日報、アーカイブ、静的ファイル、ログインとログアウトを一通り確認する。
    • 再起動・再配置をして、DBが残ることとエラーが記録されることを確かめる。

    次へ進む目印:空データの検証環境で主要画面と操作が使える。

  7. 2人以上で、見えない・変えられないことを確認する

    受け入れ確認
    • メンバーA・Bでログインし、タスク・日報・記録が互いに見えないことを確認する。
    • 別の人のタスクIDを直接指定した操作も拒否されることを確認する。
    • 上司は必要な一覧を閲覧でき、メンバーは上司画面を開けないことを確認する。

    次へ進む目印:画面表示だけでなく、直接URLや送信操作でも権限が守られている。

  8. バックアップ・復元と運用担当を決める

    守りの準備
    • DBをどこへ・どの頻度でコピーし、誰が確認するか決める。
    • バックアップから別の場所へ復元し、実際に読めることを試す。
    • SQLiteのため、まずはApp Serviceを1台で運用する。複数台への拡張は同時利用とDBの方式を見直してから判断する。
    • 利用量・エラーの確認方法と、停止時に連絡する担当者を決める。

    次へ進む目印:障害時に復旧できることを実演でき、担当者と手順が決まっている。

  9. 実データをコピーで検証してから、少人数で試す

    本番データ移行
    • 元の data/todo.db は直接上書き・移動せず、バックアップを保管する。
    • コピーDBで所有者の結び付け、タスク数・日報・親子関係・記録を確認する。
    • 確認が終わり、データ移行の許可と戻し方が決まってから、本番用の安全な移行手順を実施する。
    • まず少人数で試し、問題がなければ対象者を広げる。

    次へ進む目印:持ち主とデータが正しく、利用者が実業務で一通り使える。

全段階の確認がそろった？いいえ → 実データを入れず、該当段階へ戻って解決する

はい:利用者へ開始を案内し、バックアップ・ログイン・利用量を定期的に確認する運用へ。

「Azure導入完了」と言える目印

  • AzureのHTTPSアドレスから、アプリが再起動後も安定して開く。
  • Microsoft Entra IDで本人を確認し、許可された人だけが利用できる。
  • メンバー同士のデータが分かれ、上司画面は上司だけが閲覧できる。
  • 既存データの持ち主と記録が正しく引き継がれ、別ユーザーへ混ざっていない。
  • DBの保存場所が永続領域で、バックアップからの復元を実際に確認できている。
  • 費用・利用上限・運用担当・障害時の戻し方が関係者に共有されている。

実データを守るための注意

  • data/todo.db は本物の記録。試験・移行確認には必ずコピーを使う。
  • 開発用ユーザー選択はパスワードなしのローカル試用。本番Azureでは有効にしない。
  • 無料プランの有無・上限や、永続保存・バックアップの仕様は変わる可能性がある。作成当日にAzureの最新情報と社内ルールを確認する。
  • Azure公開や実データ移行は、権限・費用・データ保存の承認がそろうまで実施しない。

この資料は、現在の実装状況とリポジトリ内の計画をもとにした進め方です。Azureの設定値・プラン・保存仕様は、実施前に最新のMicrosoft公式情報と社内ルールで確認してください。
